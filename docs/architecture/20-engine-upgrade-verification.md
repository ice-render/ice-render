# 20 · 引擎升版后的应用侧验证清单

> **这是一份给"升级引擎的人"用的操作清单**，不是架构说明。起因：2026-09-14 给 ice-chart 与
> ice-entity-designer 对齐 ice-render 2.3.2 时，**手工**做了同一套验证，每次都能挖出东西
> （静态层到底有没有参与、hover 路径上的命中开销、以及一个 48/255 的像素差疑问），
> 而这些**现有门禁一个都覆盖不到**。本文把那次的做法、判据和踩过的坑固化下来。

## 0. 一页速览

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 | 对齐 `devDependencies` 里的引擎版本 | `npm install -D ice-render@X.Y.Z --prefer-online`；`node_modules` 与 lockfile 三处版本一致 |
| 2 | 跑该工程的门禁 | lint / types / build / 单测 / e2e 全绿 |
| 3 | **全部示例页逐页冒烟** | 无 pageerror + `window.ICE` 存在 + 画布**内容像素占比** > 2%（导航页无画布，列外） |
| 4 | **定向检查**（按本次引擎改了什么选做） | 见 §2：静态层是否参与、hover/命中路径、序列化往返 |
| 5 | 发布三件套 | 见 §4：依赖/远端/CHANGELOG 的约定与坑 |

## 1. 为什么现有门禁不够

- **应用侧 e2e 覆盖的是"主路径页面"**：ice-entity-designer 的 e2e 覆盖 8 个编辑器页，
  `power-symbols.html` 与 `water-symbols.html` **从来没人跑** —— 它们坏了不会有人知道。
  （2026-09-14 已补 `e2e/examples-smoke.spec.ts`；ice-chart 早就有同款。）
- **引擎行为改动不会让应用的单测变红**，但会改变渲染路径 / 性能 / 像素：
  例如静态层**默认开**（改变了哪些组件走位图）、命中测试换了实现（hover 路径每次 mousemove 都走它）、
  视口手势那一帧不再建位图。这些只能用"跑真实页面 + 对照像素/耗时"发现。
- **像素差只在特定形状下出现**（密集文本、组件重叠、底下已有墨迹、视口缩放态），
  随手点开一个示例是看不出来的 —— 需要**刻意构造**对照（见 §3）。

## 2. 三条定向检查（按引擎改动类型选做）

**a. 静态层位图**（引擎 ≥2.3.2）

- 先看**它到底有没有参与**：读 `ice.renderer.__layerBuilds`。
  **不要**假设"新引擎就一定会用"—— 层要求 z 序上连续 ≥256 个干净组件；
  ice-chart 的图表实例只有 15~23 个组件，实测 `__layerBuilds` 恒为 0（不参与 = 无收益也无风险）。
- 再跑**层开 / 层关像素对照**（口径见 §3）：`renderer.setStaticLayerEnabled(false)` 作对照。

**b. 命中 / hover 路径**（引擎 ≥2.3.2 换了实现）

- 逐次 `mousemove` 做命中的应用最先受影响（如 `ice-web-components` 的 `ICEHoverManager`、
  `ice-chart` 的 `HitResolver`）。
- 做法：跑该仓自己的悬停/交互探针（ice-chart 有 `scripts/hover-sweep.mjs` 与
  `scripts/audit-interactions.mjs`，后者 323 步含几何断言），或手写"逐点悬停 + 断言无报错/无残留像素"。

**c. 序列化往返**（引擎动了持久化时）

- 有快照 / 导入导出的工程：save → load → 结构化或逐像素比对；
  注意引擎的类型标识是 `namespace:Type`（见 AGENTS 的类型注册铁律）。

## 3. 像素对照的方法与口径（重点）

**方法**：同一场景开两个实例（A 关闭被测特性、B 默认），逐步驱动**相同操作**，
每步 `getImageData` 逐像素比。可运行参考：
`e2e/visual/static-layer-pixel.spec.ts`、`e2e/visual/component-cache-fidelity-repro.spec.ts`。

**判据分两档**（2026-09-14 实测，别拿一档去套另一档）：

| 场景 | alpha | 单像素 |
|---|---|---|
| 简单（少量大对象、互不重叠、透明底） | 逐位相同 | 预乘 ≤3/255 |
| 密集 / 重叠（文本密集、组件交叠、底下已有墨迹） | 差异像素 ≤1.4%、alpha 差占比 ≤0.5% | 最大通道 ≤5、最大预乘 ≤2 |

**放大因素**：组件重叠 > 底下已有墨迹 > 视口缩放（缩放会改变布局与重叠程度）。
实测视口 `scale = 1` 时两条路**逐位一致（0 差）** —— 所以看到差，先确认是不是缩放态 + 重叠。

**归因顺序**（这是这轮最省时间的一条经验，按序做能少走半天）：

1. **先量噪声底线**：同一条路径连测两次。非 0 → 页面自己在动（动画/面板），**别往下查**。
2. **切掉组件级缓存**再看差异是否消失。消失 → 差在**组件级离屏缓存**（既有机制），
   不在你正在验的新特性上。
3. **单组件对照**（CTM 只差整数设备像素）。非 0 才说明"栅格对齐"真出了问题。
4. **主画布 vs 离屏画布**（同一批内容、同一矩阵）。非 0 才说明"光栅化后端"有差异。
5. **位图边界外扩 / 强制重建位图 / 关掉视口裁剪** —— 这三条都**不改变数值**时，
   说明既不是"墨迹被切掉"也不是"位图陈旧"（本轮实测三条全不改变，白查了半天）。

## 4. 发布三件套：约定与踩过的坑

发版流程本身见 AGENTS 的「分支与发版铁律」：临时分支 → 合入集成分支
（引擎 `dev`→`master`；其它工程 `main`/`master`）→ **跑门禁** → `npm publish` → 推双远端
→ 确认「集成分支与发版分支内容一致」。

| 坑 | 现象 | 处理 |
|---|---|---|
| **本地 npm 缓存** | `npm install ice-render@新版本` 报 `ETARGET: No matching version found`，而 registry 上明明有 | 加 `--prefer-online`；`npm view` 对新版本也有传播延迟，**以 `npm publish` 的输出为准** |
| **第二远端名字不一致** | `git push github-origin ...` 报「权限/仓库不存在」这类误导性错误 | 家族里 `github-origin` 与 `origin-github` **两种都有** —— 先 `git remote -v` 看真名 |
| 推送瞬时失败 | `failed to push some refs` | 先 `git fetch` 确认**是不是真分叉**；本轮实测有一次是瞬时故障，**重试即成功** |
| CHANGELOG 约定不同 | 插入位置/标题格式对不上 | 各仓不一致：有仓**没有 CHANGELOG**（ice-entity-designer）、有仓是「新在前」（ice-chart）；**先看头部再插** |
| tag | 2.x / 0.x 历史都没打 tag | 要打先跟维护者确认，别擅自补历史 tag |

## 5. 一句话

**"对齐依赖 + 跑门禁"只是及格线**；真正能发现问题的是第 3、4 步：
**全部示例页逐页跑**、以及**按引擎改动类型做定向对照**（并且先量噪声底线、再逐层切变量）。
