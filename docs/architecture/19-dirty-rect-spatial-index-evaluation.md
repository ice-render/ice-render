# 19 · 脏区空间索引评估：要不要给局部重绘加一层索引

> **本文是评估记录，不是实现计划。** 起因：静态层位图（本轮已落地，见 [04](04-rendering-performance.md)）
> 覆盖了「一大段连续静态 + 少量动画」，但还有一类场景它救不了 —— **动画与静态在 z 序上交错**时，
> 连续干净段被切得很碎，成不了层；而脏区一旦分散，局部重绘的合并预算与面积门又会把它整体退回全量。
> 本文回答三件事：这个缺口有多大、加一层索引能拿回多少、以及真要做得先满足什么。

## 0. 结论速览

| 方案 | 改动面 | 风险 | 收益 | 建议 |
|---|---|---|---|---|
| **A. 只索引「干净组件」的均匀网格** | 引擎内新增约 1 个子系统（索引 + 维护 + 查询 + 区域预算重调） | 中（新热路径，像素一致性要重新验） | 实测 **≈1.9×**（24ms → 12.7ms），且只覆盖「静层不成立 + 脏区分散」那一类 | ⏳ **暂缓**：收益是百分比级，不是量级级；等真出现这类场景再做 |
| B. R-tree / 动态空间树 | 同上 + 更复杂的平衡/分裂 | 中高 | 相比均匀网格没有数量级差别（本场景查询是「小矩形问邻近」） | ❌ 不做 |
| C. 维持现状（局部重绘 + 静态层 + 全量回退） | 零 | 无 | 已覆盖编辑器主流场景（见 §3） | ✅ **当前选它** |

一句话：**它成立、也确实更快，但天花板只有约 3~4×（实测 1.9×），而且只在「静态层建不起来」
那一类场景里才用得上。** 优先级排在静态层之后 —— 先把它记下来，别现在动。

## 1. 现状：脏区判定链，以及它的真实边界

一帧的判定顺序（`CanvasRenderer.frameEvtHandler`，本轮之后）：

1. **预检**（`__preCount`）：只读 `display`/`dirty` 标志。可见脏组件为 0 → 回退全量；脏占比 > 20% → 回退全量。
2. **收集**（`__collectDirtyBoxes`）：给每个脏组件算「旧盒 ∪ 新盒」。
3. **合并**（`coalesceRegions`）：带「划算护栏」地并成若干块，上限 6 块（软上限，硬上限 24 才塌缩成一个并集盒）。
4. **面积门**：合并后的区域面积占画布 > 35% → 回退全量。
5. **相交门**（`__riskyIntersectsRegions`）：逐组件扫描，字符/点集/半透明落墨与区域相交且不可缓存 → 回退全量。
6. 通过 → `__renderDirtyRect`：**对每一块区域**清屏 + 裁剪 + 扫**整条组件队列**挑出要重画的组件。

### 1.1 决定性事实：能不能局部重绘，取决于脏区的**几何分布**，不是数量

同样 10000 个组件、同样的画布，只改「哪些组件在动」：

| 场景（10000 组件，1600×1000） | 引擎实际走的路径 | p50 |
|---|---|---|
| 每 20 个里 1 个动画（500 个）→ 脏盒排成 **4 条竖列** | 局部重绘 **30/30 帧**（4 块区域，面积占比 9%） | **6.4 ms** |
| 每 100 个里 1 个动画（100 个）→ 脏盒排成**一条斜线** | **全量重画 30/30 帧**（局部重绘 0 次） | **11.7 ms** |

**动画更少反而更慢**：斜线分布的脏盒合并不出便宜的形状，撞上面积门 → 整条退回全量。
这条比任何抽象描述都更能说明问题：**门是「面积」和「块数」，而真实的损伤分布与它们不同构。**

### 1.2 放宽合并预算这条路走不通

在真实场景（10200 组件 / 200 个分散动画）上扫预算。
**口径提醒**：这一组是用原型替换 `__collect()` 得到的（简易合并：把脏盒按序等分成 k 块），
**不是引擎真实的 `coalesceRegions`**（带划算护栏的那套）。所以请看**形状**，不要看绝对值：
放宽预算既不是单调变好、也远不足以把局部重绘救回来。

| 每帧允许的脏区块数 | p50 |
|---|---|
| 现状（6 块 + 面积门） | 23.8 ms |
| 2 块 | 14.6 ms |
| 8 块 | 22.0 ms |
| 16 块 | 28.5 ms |
| 32 块 | 32.8 ms |
| 64 块 | 36.3 ms |
| 不合并（200 块） | 36.3 ms |

非单调、且放宽只会更慢。原因在第 6 步：`__renderDirtyRect` 对**每块**区域都要扫整条队列，
是 `O(区域数 × 组件数)` —— 200 块 × 10200 组件 = 每帧 200 万次判定。
**所以「放宽预算」不是调参问题，它必须有索引兜底才有意义。**

## 2. 原型实测（本轮探针，跑完即删）

原型思路：**只索引「干净组件」**。干净组件按定义不会移动，索引一次建立后每帧只需为
「上一帧脏、这一帧干净」的那几个做删除/插入（实测 **0ms/帧**，1 万组件规模）。
查询时按区域取覆盖到的格子、去重后与「本帧脏组件」求并集，再按 z 序重画（引擎的裁剪/清屏语义不变）。

场景：2000 文本 + 1000 折线 + 7000 小矩形 + 200 个**铺满画布**的分散动画（就是 §1.2 那个 23.8ms 的场景）。

| 格子尺寸 | 每帧候选访问次数 | 每帧实画组件数 | 索引版 p50 | 现状 p50 | 加速 |
|---|---|---|---|---|---|
| 128 px | 159,959 | 3,097 | 23.1 ms | 23.1 ms | **1.0×** |
| 64 px | 48,650 | 3,024 | 15.0 ms | 23.5 ms | 1.6× |
| 32 px | 15,949 | 2,983 | 13.3 ms | 24.4 ms | 1.8× |
| **16 px** | 5,926 | 2,533 | **12.7 ms** | 24.1 ms | **1.9×** |

两条副产物结论：

- **格子尺寸是这个方案的命门**：128px 时索引等于没建（候选数和全队列一个量级）；要细到 16~32px 才有意义。
- **「一次 clip 剪到多区域并集」的变体更慢**（15.0 / 17.4ms vs 逐块 13.3 / 15.0ms）：
  带几百条子路径的复合裁剪区会拖慢它覆盖的每一次绘制。裁剪必须逐块。

### 2.1 为什么天花板只有 3~4×

把账算清楚（10200 组件的那一帧）：

| 项 | 量 |
|---|---|
| 全量重画：10200 个组件 × ≈1.9 µs | ≈ 19 ms |
| 损伤驱动：每块脏区要重画与它相交的所有组件 ≈ 2500~3100 个 | ≈ 5~6 ms |
| 每帧 196 块区域各自 save/clip/clear/restore | ≈ 2~4 ms（估算，未单独量） |
| 候选收集（索引查询 + 去重） | ≈ 1~2 ms（原型第一版用 `WeakMap` 去重时这一项显著更大） |

密集场景里每个脏点会覆盖十几个组件 —— 这是「损伤驱动」的固有成本，索引消不掉。
**理论天花板 ≈ 3~4×，实测落在 1.9×。** 这跟静态层那种「整层贴回」的量级收益（9~18×）不是一回事。

## 3. 它和静态层是什么关系

本轮落地的静态层位图覆盖的是**另一个**象限：

| 场景 | 局部重绘 | 静态层 | 索引 |
|---|---|---|---|
| 大段连续静态 + 少量分散动画 | ❌ 面积门挡下 | ✅ **9~18×** | 可用（约 2×），但没必要 |
| 小范围损伤（拖一个组件） | ✅ 已够好 | 不介入 | 不介入 |
| **动画与静态在 z 序上交错** + 脏区分散 | ❌ | ❌ **连续干净段 < 256，建不起层** | ✅ **唯一可用的一档** |

三者不冲突，优先级是：**局部重绘 → 静态层 → （将来）索引 → 全量**。
索引只影响第一步的「面积门与块数上限」—— 它的真正作用是把「区域太碎就退全量」换成「区域碎也没关系，按格取候选」。

## 4. 如果将来要做：必须守住的设计点

1. **索引对象是「干净组件」的落屏快照盒**（`__snap` 里那份），不是组件本身、也不是每帧现算的盒。
   干净组件不动 → 索引天然稳定；脏组件从索引里摘掉、重新变干净时按新盒插回。
2. **维护成本必须是 O(脏组件数)**：每帧只处理「脏→干净」与「干净→脏」两个集合的差。实测 1 万组件下 ≈ 0ms。
3. **去重用组件上的戳记字段**（每次查询 `stamp++`，`c.__qstamp === stamp` 即已访问），
   不要用 `WeakMap`/`Set` —— 原型里用 WeakMap 时每帧 16 万次查询本身就吃掉 8ms。
4. **格子尺寸按组件尺寸自适应**，16~32px 量级起步；固定 128px 等于没建。
5. **区域预算放宽到什么程度要重新扫**：有了索引，`MAX_DIRTY_REGIONS` 的约束从「扫描成本」变成「区域 setup 成本」，
   原型里 196 块区域仍可接受（要盯住 merge 的护栏，别把细长盒串成整屏大盒）。
6. **`__collectDirtyBoxes` 自身仍是 O(N)**（要遍历队列找脏组件）。真要拿满收益，这一遍也要能增量取脏
   —— 例如维护一条「脏组件链」，让收集只与脏组件数相关。
7. **索引失效路径要与现有失效对齐**：结构变更（`markQueueDirty`）、视口变化、z 序重排、
   `display` 切换、组件销毁 —— 每一条都要有对应处理与回归用例。

## 5. 风险

- **像素一致性的风险面与静态层同级**：它改变的是「谁被重画」，必须沿用同一套 clip/clear 语义，
  并用与 `dirty-rect-pixel.spec.ts` 相同强度的逐步逐像素对比（含 dpr=2、非单位视口）来验。
- **收益依赖场景**：如果真实应用的损伤都是「局部、单个」（拖拽/悬停），索引一点忙都帮不上；
  它的价值只在「多个分散动画同时进行」时才兑现。
- **复杂度是长期的**：索引是一个新的常驻数据结构，失效路径漏一条就是「画面不更新」这类最难查的 bug。

## 6. 验收条件（真要做的话，缺一不可）

1. **像素**：`dirty-rect-pixel.spec.ts` 的全部场景 + 新增「分散脏区 / 交错 z 序」两个 fixture，
   与全量逐步逐像素一致（口径同现有：full vs 局部 100% 一致）。
2. **不回退**：`bench 2000 --check` 的场景 A/B 不得变慢（索引维护是每帧固定开销）。
3. **量级**：新场景（交错 z 序 + 分散动画）进入真浏览器基准，p50 至少要**降到现值的 1/1.5 以下**，
   否则这个子系统不值得背。
4. **降级**：任何异常都必须被捕获并回退到现有路径（帧回调里抛异常 = 未捕获异常 / 页面白屏）。

## 8. 建议

**暂缓。** 理由是本轮实测出来的收益比（1.9×，且只覆盖一个象限）与它的长期复杂度不成比例，
而**已经落地的静态层把主流场景拿走了（9~18×）**。

建议的触发条件：当应用侧真的出现「多个分散动画同时进行、且静态层建不起来」的场景
（典型信号：`__layerBuilds` 长期为 0 而 `__collect` 长期返回 null），再把本文的 P1~P3 排上。
届时**先做一次现场度量**（在真实应用里量 `__collect` 的返回情况与帧耗时），
用真实数据确认这 1.9× 值得，再动引擎。
