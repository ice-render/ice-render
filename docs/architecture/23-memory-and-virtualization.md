# 内存与虚拟化：决策记录

> 这一页是**内存这一块"做了什么、为什么这么做、否决了什么"的决策记录**，不是 API 手册。
> 所有数字都来自**真机 Chrome + V8 堆快照 / CDP 探针**（口径见文末 §6）。
> 与渲染性能的日常口径见 [04 渲染与性能](04-rendering-performance.md)；虚拟子源的分期设计见仓库内
> `plans/virtual-child-source.md`。

## 1. 一句话结论

10 万图元的内存**从 648.5 MB 降到 171.3 MB**（累计 −73.6%）；其中最后一批四刀是
**234.6 → 171.3 MB（−27.0%）**，堆节点 **681.5 万 → 454.9 万**。
再往上一个数量级靠的不是"更快"，而是**让看不见的图元根本不存在**：IED 的真实工艺图
（2,000 符号 / 6,000 条目）**235.3 MB → 7.4 MB（−96.9%）**，20,000 符号档（60,000 条目）
虚拟文档 **23.8 MB** 跑 120 fps，而对象模式**构建即把标签页拖死**。

## 2. 内存都花在哪了：先看成本剖面

10 万图元（`examples/performance/bench-scene.html`）的堆快照说得很直白：

| 项 | 改前 | 说明 |
|---|---|---|
| 全堆自有大小 | 234.6 MB | 每图元约 **1.7 KB** |
| 堆节点数 | 681.5 万 | 每图元约 **29 个堆对象** |
| `(object elements)` | 103.9 MB | 各类对象的**属性/元素存储**（props / state / style / 数组元素…） |
| `system / PropertyArray` | 22.1 MB | 超出「对象内属性」区之后的属性存储 |
| `Object` | 31.3 MB | 700 万个普通对象（props / state / 监听记录 / 矩阵…） |
| `Array` | 19.8 MB | 130 万个数组对象（头部 + 元素） |
| `Float64Array` + `ArrayBuffer` | 10.7 MB | 其中 **10 万个 JSTypedArray + 10 万个 ArrayBuffer 只为存 32 字节**（上屏快照盒） |

**结论：钱花在"记账"上，不花在数据上。** 十个字段的几何 + 样式加起来不到 20 MB，
剩下 200 MB 全是"每个图元一个对象"这件事本身的开销。所以后面每一刀都问同一个问题：
**这个每图元对象，真的需要存在吗？**

## 3. 决策点（每一刀都先量再改）

| 决策 | 选择 | 依据 / 效果 | 当时**否决**的做法 |
|---|---|---|---|
| 默认 props / state | **原型共享**（`Object.create(DEFAULTS)`），只物化显式键 | 100 万最小矩形堆内存 −56%（2026-09-10，`00eaf7b`） | 每实例显式传整份默认表（实测 6.86 KB/实例 vs 1.49 KB） |
| 空容器对象 | `__gradCache` / `__uiStates` **按需创建**（`null` 起步） | 每图元少 2 个空对象；`{}` 在 10 万图元下并不便宜 | 保持 `{}` 默认（当时省事的写法） |
| 几何签名 `__pathSig` | **双 32 位哈希**（长度 + h1 + h2，共 12 字节） | 签名只用于"和上次一样吗"，却按图元常驻 11.7 MB；碰撞漏判概率 2⁻⁶⁴ | ① 存签名数组（原做法）② 只存 h1（碰撞概率 2⁻³² 不够放心） |
| 引擎默认事件监听 | **类级声明 + 派发时解析**（不进 `listeners`） | 每图元少 3 个数组 + 3 条记录 + 1 份属性存储；语义逐条保住（`off`/`hasListener`/`suspend`/`purgeEvents`/子类覆盖 `initEvents` 不调 `super`） | ① 逐实例注册（原做法）② 用实例字段记开关（违反「热路径类不加实例字段铁律」，实测 3~4× 退化） |
| 上屏快照盒 `__snap` | `WeakMap` 存**槽位号**（Smi）+ 分块 `Float64Array` arena | 省掉 10 万个 JSTypedArray + 10 万个 ArrayBuffer（10.7 MB）；数据从散块并成连续内存 | ① 每组件一个 `Float64Array(4)`（原做法）② 也想过"干脆不存快照"，但视口裁剪与脏区擦除都靠它 |
| 同几何图元 | **共享 `Path2D`**（按「类 + 几何签名」查有界缓存） | `Path2D` **100,018 → 24**，堆 330.6 → 234.6 MB | 每图元一份路径（原做法） |
| 临时缓冲 | 模块级共享 + `suspendedEventNames` 按需 | 每图元常驻数组 **38.3 → 27.3**，堆 371.0 → 330.6 MB | 实例级 scratch（"反正只分配一次"） |
| 视口变化的失效面 | `setViewport` **只请求整屏重画**，不清队列 / 快照 / 静态层 | 10 万图元平移 **9.9 → 116.6 fps**、长任务 28 → 0（详见 [11 视口缩放](11-viewport-zoom.md)） | 沿用 `markQueueDirty()`（把"视图状态"当"结构变更"） |

### 3.1 明确**否决 / 暂缓**的（同样是决策，写下来免得反复讨论）

| 候选 | 估算收益 | 为什么不 | 备注 |
|---|---|---|---|
| `state.linearMatrix` 每组件 `Float32Array(6)` + `ArrayBuffer` | 10.7 MB（共享 slab 只省其中约 5 MB） | 视图对象仍然每组件一个；且要给 slab 配"销毁即归还"的生命周期 | 留档，等有足够大的收益一起做 |
| 每组件 5 个数值数组（`composedMatrix` / `localOrigin` / `absoluteOrigin` / `absoluteLinearMatrix` / `dots`） | 约 15 MB | 矩阵按**序列化契约**必须是普通 `Array`（`Array.isArray` 与快照都依赖它） | 同上 |
| `id` 惰性生成（`ICE_` + uuid） | 约 7.1 MB | `id` 是公开字段（A2UI / 业务绑定 / 快照都读它），改惰性会牵动序列化与绑定 | 同上 |
| SoA / ECS 内核化 | 理论 10×+ | 等于换内核：`component.state.left` 这套公开契约、子类化、每实例监听全部作废 | **架构层面**否决，不是"以后再说" |
| 遮挡剔除（被挡住的图元不画） | 实测**只值 1.6%** | 三个真实场景（压测场景 / IED 工艺图 / XP 桌面）里"完全被不透明块覆盖"的图元几乎不存在；2D 画家算法下"被挡在后面"≠"不用画" | 2026-09-21 实测否决，结论见 04 |
| LOD（亚像素图元不画） | 0.1× 缩略视图 −54.8% | 落地了，但**默认关闭**（会改变显示结果，由宿主决定） | `setLodMinDeviceArea(px²)` |

## 4. 虚拟子源：从"记账成本"到"不存在的对象"

上面的四刀把"每图元的记账成本"压到接近下限 —— 再往下只有一条路：**让看不见的图元根本不是对象**。
这就是「虚拟子源」：文档用紧凑列存（SoA）当唯一真相，引擎只为**可见窗口**内的条目建真组件。

### 4.1 决策点

| 决策 | 选择 | 为什么 |
|---|---|---|
| 子源放在引擎层还是各应用自己写 | **引擎层**（`VirtualChildSource` 契约 + 容器接入） | 命中 / 选中 / 控制面板 / 导出 / 序列化 / undo **都要读同一份数据**，各写一遍必然"渲染能虚拟、选中就崩" |
| 坐标系 | **容器局部坐标**（引擎把可见窗口经逆合成矩阵变换过去） | 虚拟容器才能像任何组件一样被摆放 / 嵌套 / 放进变换组；常见用法（在原点、无变换）下局部 == 世界 |
| 命中语义 | **命中即物化 + 事件重定向**（可切 `container` 策略） | 上层（`evt.target`、选中、控制面板、拖动）完全不用知道虚拟化；移动类事件不做命中检测，所以 hover 不会批量物化 |
| 批量落墨 | 应用实现 `paint(ctx, view)`，引擎**包一层 `save/restore`** | 隔离 ctx 状态：不隔离时"容器自己的盒子"会被**最后一个图元的颜色**填满（真机实测：整屏变紫、像素对拍 99.9% 不一致） |
| 静态层 | 虚拟容器**永不入层** | 它的内容依赖视口；烤进位图后平移会把**旧窗口**整体挪走 |
| 窗口内增删 | `markWindowChanged(child)`：队列照重建，但**保留其他组件的上屏快照** | 老路径（清全部快照）在 10 万图元世界里一次 `addChild` = **117 ms** |
| 导出 / 序列化 | 导出走 `paintToSvg(sink, bounds)`（全量文档）；序列化写 `virtual: {type,count,version,payload}` + 物化子项的 `virtualIndex` | 应用反馈（IED）暴露的硬需求：只看组件树的话，导出与存盘**都只剩窗口里那点** |
| 文档写入 | `applyPatch(i, patch)`（唯一写入口）+ 物化组件改动经 `onChildPatched` 回流 | "文档是真相、组件是投影"必须落到代码上的**一个入口**；否则 undo 记在物化组件上，物化/回收就丢历史 |
| 窗口内物化循环 | 引擎提供 `syncVirtualWindow(container, {needs, map, pad, budget})` | 每个应用各写一遍会踩同样的三个坑：滞后带、每帧上限、`map`（访问的下标 ≠ 要物化的下标） |

### 4.2 实测（同几何对拍）

| 指标 | 对象树（现状） | 虚拟子源 |
|---|---|---|
| 堆（10 万图元） | 173.8 MB | **5.8 MB**（纯批量）/ 6.9 MB（1/3 带标注的混合） |
| 堆节点 | 548 万 | 4.7 万 |
| 单帧（强制全量重画，1×） | 123.1 ms | **0.3 ms** |
| 单帧（0.1×，几乎全在屏） | 180.4 ms | 44.4 ms |
| 平移（官方 API） | 116.6 fps | **121.2 fps / 0 长任务** |
| 命中（空点最坏 / 命中图元） | 3,994 µs / ~3.2 µs | **0.15 µs** |
| 按需新建 1 个图元 | 117 ms | **0.3 ms** |
| 像素一致性 | — | 差 3/1,600,000（0.0002%），最大通道差 9/255 |
| 100 万图元 | 建不起来 | **32.0 MB**、窗口内画 6,653 个、单帧 1.1 ms |

真实业务侧（IED 给排水工艺图，`examples/water-large.html`）：2,000 符号（6,000 条目）
**7.4 MB vs 235.3 MB**；导出 SVG 从"只有窗口"（102.9 KB）变成**整份文档**（7.46 MB）；
快照只存"参数 + 少量编辑"（5,000 符号档 133.6 KB）。

### 4.3 边界（不是万能药）

- **收益 = 看不见的比例**：场景"全都在一屏"时堆不变，只有每项成本那点收益（上表 0.1× 那一档）。
- **文字 / 图片 / 自定义子类**走"窗口内物化"（混合策略），不是批量落墨；这类文档的内存是 O(窗口)。
- 应用要自己提供：列存文档、空间索引、`paint`（或 `materialize`）、导出描述。IED 的参考实现约 350 行。
- worker 镜像**目前只含物化子项**（引擎会告警一次）；文档下发未支持。

## 5. 纪律（每次改内存都要走这一套）

1. **先量再改**：真机 Chrome + CDP 抓 V8 堆快照，看"全堆自有大小"与**堆节点数**；
   探针脚本在 `bench/`（引擎内）与真机 CDP 脚本（不入库）里。
2. **A/B 必须同机**：改动前构建与改动后构建各抓一份，别拿历史数字凑；
   本文所有"改前/改后"都是同机同页面几分钟内的两次采集。
3. **回归三件套**：`npm run verify:full`（含 111 条 Playwright 像素回归 + 四组基准）、
   家族全量回归（`scripts/family-regression.cjs --tier=full`）、以及**真机交互探针**
   （拖动 / 平移 / 命中的 fps 与长任务）。
4. **别给热路径类加实例字段**（见 AGENTS）：一个布尔字段就会让整条继承链的属性访问退化 3~4×；
   需要"每实例一个值"时用 `state`、模块级 `WeakMap`/`WeakSet`，或挂在既有对象上（如 `listeners` 的 Symbol 键）。
5. **每图元一个对象要有代价意识**：加新对象前先问"10 万图元时它是多少钱"。

## 6. 口径与复现

- **口径**：真机 Chrome（CDP）+ `examples/performance/bench-scene.html`；堆口径是 V8 堆快照的
  **全堆自有大小**（不是 RSS）；帧率是**真实 rAF**，场景为"每帧平移 3px"或"每帧全量重画"。
- **复现**：`examples/performance/bench-scene.html?n=100000&mode=static|anim|fps`；
  堆快照用 CDP 的 `HeapProfiler.takeHeapSnapshot`，分析脚本按"类型 / 构造名 / 一层出边"聚合。
- **已知噪声**：全量重绘的**中位数**在 ±5% 内波动（最小帧更稳定）；跨机比较没有意义，
  只看同机 A/B。

## 7. 业务工程验证（2026-09-21，真机 Chrome / CDP）

引擎自己跑得好不等于业务工程跑得好。所以这一节是**在真实业务工程里**量的：
同一台机器、同一页面，用**已发布的 4.1.0** 与**当前工作区引擎**各跑一遍（打包型应用重建后再跑），
量 JS 堆（GC 后）、交互帧率（滚轮缩放 + 拖拽平移）、长任务、控制台报错。

### 7.1 轻量业务页：确认**没有回归**（两边数字一致）

| 应用 | 页面 | 堆（4.1.0 → 工作区） | 交互帧率 | 长任务 | 报错 |
|---|---|---|---|---|---|
| ice-smart-water | 首页（21 块画布） | 9.2 MB → 9.2 MB | 120.6 → 120.5 fps | 0 → 0 | 0 → 0 |
| ice-agent-console | 首页 | 33.8 MB → 33.8 MB | 120.5 → 119.9 fps | 0 → 0 | 0 → 0 |
| ice-game | Windows XP 桌面 | 8.9 MB → 8.9 MB | 120.8 → 120.8 fps | 0 → 0 | 0 → 0 |

这三个页面的图元量级不大，**看不出差异是正常的** —— 它们的价值是"证明这一轮改动没有把已有业务拖慢"。
真正吃内存/帧率的是"文档大、屏幕小"的业务场景，见下。

### 7.2 业务规模：同应用同 API 造 2,000 个工艺符号（IED 水务编辑器）

用 `ice-entity-designer` 的**自己的 API**（`designer.createSymbol` / `createPipe`）在 `water-editor.html`
里建 2,020 个符号 + 2,020 条管线，然后量堆与**官方 `setViewport` 平移**帧率：

| 同一份 2,000 符号的水务图 | 堆（GC 后） | 官方 `setViewport` 平移 |
|---|---|---|
| 真实组件 + 编辑器历史快照 | **932.8 MB** | 110.7 fps / 0 长任务 |
| 真实组件（`resetHistory()` 之后） | **58.4 MB** | 110.7 fps / 0 长任务 |
| 虚拟文档（`examples/water-large.html?n=2000`，同 domain / 同 API） | **7.4 MB** | 120.2 fps / 0 长任务 |

三条结论：

1. **视口那一刀在业务里是真实生效的**：这条平移走的是官方 `setViewport`，在当前引擎上 110.7 fps / 0 长任务；
   同一操作在旧引擎上是"每帧重建队列 + 清快照"（引擎级 A/B：9.9 fps / 28 个长任务），业务侧量到的差距就在这里。
2. **虚拟文档把"组件树本身"再压掉一个数量级**：58.4 MB → **7.4 MB（−87%）**；
   相对"带历史的 932.8 MB"是 −99.2%。
3. **最大的那一块不在引擎，在应用的编辑器设计**：932.8 MB 里 **874 MB（94%）是"每次改动全量快照"的历史**
   —— 建 2,020 个图元花了 **58.5 秒**（≈29 ms/个，因为每次 `createSymbol` 都 `__captureHistory()`）。
   这条与"undo 要改成文档补丁"是同一件事（见 §4.1 的"文档写入"行与 IED 的反馈文档）。

   **已修**（同一天）：IED 加了 `beginBatch()/endBatch()`（批内不逐条记历史，整批算一条）与**按留存字节**
   的历史封顶（默认 32 MB / 条数上限照旧 100）。复测同一份 2,020 符号 + 2,020 管线：
   建场景 **58.5 s → 14.4 s**、堆（含历史）**932.8 → 58.5 MB**，交互 118.6 fps、
   官方 `setViewport` 平移 108.4 fps / 0 长任务（组件树本身仍是 58.4 MB）。
   **这条经验对引擎有普适性**：任何"每次改动整份序列化"的簿记（历史 / 自动保存 / 协作同步）
   在万级文档上都会变成内存与耗时的主项 —— 先量它，再谈优化引擎。

> 探针：应用侧真机验证脚本在 `/tmp/biz-verify/probe.mjs`（会临时软链引擎 + 重建 + CDP 采集，跑完还原）；
> 引擎级 spike 探针在 `/tmp/ice-virt-spike/probe.mjs`。两者都不入库，口径写在本节里。

## 7. 仍未做（写在这，免得反复讨论）
